# Diagram library: architecture elements and compositions

For complete object XML, including 3D and inherited style references, consult the [source object style records](source-object-styles.md) as well as the diagram-specific shape index.

Use the [source diagram deck](../assets/Diagram%20library%20-%20Diagram%20Elements.pptx) with its [component and composition index](diagram-library-index.json) and [per-shape style data](diagram-shape-styles.json) for relevant architecture, systems, data-flow, ownership, platform and activation diagrams. Its 15 slides comprise reusable elements and guidance (1–5) plus ten varied full architecture examples (6–15). It is a specialized architecture reference, not a complete library of generic flowcharts, statistical charts, or every business diagram; for those, consult the wider slide library and adapt to the information relationship.

## Selection and composition

1. Identify the message, audience and actual relationships: sequence/direction, containment, ownership, responsibility, dependencies, integration mechanism, timing, and evidence status. Draw only relationships supported by the current project.
2. Select a composition before styling: input → platform → orchestration → activation (6, 11); two environments and transfer (8–9); multi-system ecosystem (10, 15); diagram with explanatory notes (12–13); or linear processing chain and separate orchestration (14). Page 7 distinguishes a customer environment from a separate identity-services layer. Choose only relevant elements and simplify or split dense diagrams.
3. Define outer zones from real ownership, responsibility or function. Page 1 offers white, light-blue, light-gray and lavender zones, nested subzones, dashed or solid highlights, internal dividers and numbered callouts. Inspect each relevant source shape's actual fill, gradient stops and direction, opacity/transparency, border and shadow; preserve meaningful distinctions between examples when adapting their styles. A nested box communicates inclusion; crossing an ownership boundary does not imply data can move freely. Add a legend when multiple visual codes are used.
4. Populate zones with consistent component cards (page 2), storage cylinders only where their meaning fits, and authorized logos or icons. Distinguish ordinary, secondary, branded and emphasized components through documented fill and text contrast. Page 2 shows client-colored zone outlines and subtle gradients, but only when actual ownership and branding justify them.
5. Add directional connectors according to actual interface and data movement. Source page 3 proposes 1 pt solid = batch and dashed = streaming; API #0391F2, data share #0935AD and zero-copy #AEAEBC; success #05B050 and failure #B02418 at 2 pt. These are source-specific conventions: use a clear legend and adapt when another approved convention applies; do not imply an interface or implementation exists solely from a reference.
6. Use page 4's icon conventions only where they fit: user/device/input examples use indigo gray #5F607C; the source caps **Mini Fill icons** at 0.25 inches (0.635 cm). Consult the [icon semantic index](icon-usage.md) for meaning and appropriate medium alternatives. Page 5 shows platform marks for light/dark backgrounds; use marks only when relevant and permitted.
7. Construct text, cards, zones, lines and connectors as editable, groupable native PowerPoint elements; preserve natural text wrapping. Some source icons and logos are picture objects, not editable vector shapes; preserve them as separate assets where appropriate rather than claiming the internal artwork is editable. Validate arrow direction, labels, contrast, overlaps, layering, page margins and legibility in the target PowerPoint. Avoid using a flattened screenshot as the diagram.

## Source styling details

The source describes a white general-zone fill #FFFFFF with shadow transparency 90%, size 100%, blur 28 pt and distance 4 pt. It labels data/platform #E8F0FE, orchestration #E5E5E9 and analytics #D6D6DF (page 1). **The actual analytics parent shape (page 1, shape ID 14) has direct fill #DADAF2, despite its #D6D6DF text label.** The label and the actual object property are distinct evidence; inspect the original when deciding which to reproduce. The same applies to documented versus actual effect values.

The [per-shape data](diagram-shape-styles.json) captures direct shape fills, gradient stops, OOXML angle, opacity, color transforms, outlines, geometry and effects across all 15 slides, with slide number and shape ID. Missing direct properties can inherit from a style or theme: they are not automatically no fill or zero transparency. Theme references and transforms are recorded without claiming resolved RGB values; use the original source deck and its theme to verify the rendered result. Group-child coordinates are relative to the group. These are optional local visual encodings, not universal meanings. When using multiple examples together, consciously reconcile differences in palette, gradient, opacity, outline, corner shape, hierarchy, spacing and legend; don't mix incompatible encodings. Arial / 微软雅黑 and current user instructions override source fonts. Never reuse reference client names, logos, system relationships, case descriptions, metrics or claims as current-project evidence.
